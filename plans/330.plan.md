Guiding rule (from the request, keep verbatim in `doc/arc42`'s chapter 1 as a working principle):

> If removing a detail would not change a stakeholder's understanding of the architecture or an architect's fundamental implementation choices, that detail probably belongs in the Obsidian knowledge graph instead.

### 1.1 Truth model and precedence

The table in §1 says *where a topic's content lives* (division of labor). It says nothing about *who wins when two artifacts disagree about the same current-state fact*. That's a separate axis, and every skill in §8 must respect it:

- **The code is the truth.** Tests prove the implementation.
- **`doc/arc42`** gives the bird's-eye view.
- **`openspec`** defines what *must* be true — the contract, not necessarily what's implemented yet (see §5.3: a spec intentionally running ahead of the code, tracked via an ADR and a risk entry, is a documented *gap*, not a *contradiction* — this precedence rule is for resolving the latter).
- **The Obsidian knowledge graph explains details.** Every note is a **hypothesis about the code**, never an independent fact — it's only ever as good as it was last checked.

**Order of precedence when artifacts contradict:**

1. Code and tests
2. `doc/arc42`
3. `doc/concept`
4. `openspec`
5. `obsidian`

**How a contradiction with a knowledge note gets resolved** (this is normative for the `knowledge-maintainer` skill, §8):

- If a knowledge note contradicts the current code: check the note against the code, and **follow the code**.
- Then correct the note and set its frontmatter `updated:` date to record that it was re-verified and fixed.
- If it isn't possible to check (the agent can't run/read the relevant code, or the answer is genuinely ambiguous): set `status: stale` with a one-line explanation of *why* it couldn't be verified — never paper over the gap with an educated guess.
- **Never let an unverified knowledge note drive an implementation decision.** When a note's claim can't be confirmed against code, that must be surfaced as an explicit, visible contradiction (e.g. a callout in the note and in whatever the agent is producing) — not silently trusted and not silently dropped.
- `status: superseded` and `status: stale` are **historical records, not instructions for action.** An agent that finds a note in either state must go verify against the code (or a more authoritative artifact per the precedence list) rather than treat the note's content as current guidance.

> **Hard rule — no implementation changes.** Every phase of this plan (A–G) touches only documentation/specification artifacts: Markdown, AsciiDoc, and skill front matter under `openspec/`, `obsidian/`, `doc/arc42/`, `plans/`, `.agents/skills/doc/`, and `AGENTS.md`. This plan **must not** create, edit, or delete any `.java`, `.js`, `.ts`, or Gradle file (`*.gradle`, `settings.gradle`, `buildSrc/**`) — or any other implementation/build file. Where a phase's content *describes* implementation (e.g. the `security` capability referencing `EsySecurityConfiguration`, or the decommission gate in §11.2 touching `settings.gradle`/`playwright.test.sh`/`compose.yml`), that description is documentation only — the actual file change is explicitly out of scope here and deferred to a separate, later change. If executing any phase below appears to require touching an implementation file, stop and split that work into its own plan instead of doing it here.

## 5. OpenSpec (`openspec/`)

### 5.1 Directory structure (standard OpenSpec layout)

```
openspec/
├── project.md                         # tech stack, conventions, tooling — read by every agent first
├── AGENTS.md                          # OpenSpec's own agent instructions (generated by `openspec init`)
└── specs/                             # current, merged truth — one capability per folder
    ├── rest-conventions/spec.md
    ├── graphql-conventions/spec.md
    ├── security/spec.md
    ├── client-shell/spec.md
    ├── owner-management/spec.md
    ├── pet-management/spec.md
    ├── vet-management/spec.md
    └── visit-management/spec.md
```

`openspec/changes/` is **not a persisted repository artifact**. A change proposal (`proposal.md`, `tasks.md`, optional `design.md`, delta `specs/<capability>/spec.md`) is working state only — drafted locally (or on a short-lived branch) while a change is designed and reviewed, then applied straight into `specs/` and discarded, never committed to the repo on its own. `openspec/changes/` is listed in `.gitignore`. The record of *why* `specs/` changed at a point in time is the commit/PR that changed it, same as any other source file — no separate persisted change-tracking layer, no archive.

Bootstrapping via `openspec init` first, then hand-author `project.md` and the capability specs above as the **initial baseline** — since there is no prior OpenSpec content, the first population is drafted as one working "baseline" change and applied straight into `specs/` in a single commit, rather than persisting a `changes/` folder for it.

### 5.2 Capability catalogue and requirement coverage

Two kinds of capability: **cross-cutting conventions** (apply to every entity) and **per-business-capability** specs (Owner/Pet/Vet/Visit) that reference the conventions instead of restating them. Each capability's requirements use OpenSpec's `#### Scenario:` (Given/When/Then) format.

**Cross-cutting capabilities**

| Capability | Covers (from the request) |
|---|---|
| `rest-conventions` | Commands vs. queries; PATCH JSON format (JSON Merge Patch, one field or a validated subset per request); ETag versioning (`If-Match`/`If-None-Match`, 412 on mismatch); request/response semantics (status codes, content types); request filtering (query-param based, case-insensitive `contains`/`startsWith`); response pagination (`page`/`size`/`sort`, HAL-style page envelope); validation behavior (400 + field-level errors); error handling and error codes (400/404/409/412 mapped consistently via `RestControllerAdvice`) |
| `graphql-conventions` | Request/response semantics (query vs. object vs. batch-loaded relation resolvers); validation behavior; error handling and error codes (GraphQL errors `extensions.classification`) |
| `security` | **Baseline, as-implemented today**: CORS (origins, credentials, headers, methods, max-age, private-network — mirrored from the actual `Cors` helper); stateless sessions; CSRF disabled; **no authentication or authorization is currently enforced on any endpoint**. Explicitly does *not* yet specify roles/scopes/claims or JWT validation — that arrives as a dedicated future OpenSpec change (see §5.3), not as part of this baseline |
| `client-shell` | UI patterns every generated screen must follow: lister/editor/viewer navigation flow, pagination/filter controls, optimistic-concurrency handling (surface 409/412 to the user, offer reload), validation error display, auth/session handling (token storage, redirect-to-login on 401), error/toast conventions, loading states |

**Per-business capabilities** (`owner-management`, `pet-management`, `vet-management`, `visit-management`), each `spec.md` structured as:

```
## REST Requirements       (endpoints, fields, relations — references rest-conventions)
## GraphQL Requirements     (queries/mutations, fields — references graphql-conventions)
## UI Requirements          (required screens/actions — references client-shell)
```

These stay entity-specific and technology-agnostic about *implementation* (no Spring/Angular/Svelte detail — that's `doc/service/*.adoc` and Obsidian's Backend/Frontend categories). They are the single source of truth an AI reads to regenerate a client capability end-to-end.

### 5.3 Roles, permissions, and JWT resource server — future plan, prepared for here

Introducing roles/permissions and turning the backend into a JWT-protected resource server is **its own future plan**, out of scope for phase A. This plan's responsibility is to make sure that future plan has a clean landing spot instead of having to restructure OpenSpec/Obsidian/arc42 when it arrives. Concretely, phase A/B/C produce:

1. **`openspec/specs/security/spec.md` scoped to the current baseline only** (§5.2 table) — written so the future change adds a `## ADDED Requirements` delta (roles/scopes/claims, JWT validation) under the same capability, rather than needing a new capability or a rewrite of the existing one.
2. **An ADR stub**, `doc/arc42/adr/0004-jwt-resource-server-and-roles.adoc`, status **`proposed / deferred`** — not a decision, a placeholder that captures the questions the future plan must resolve before it can be spec'd (carried over verbatim from this plan's earlier discussion, so they aren't lost). ADRs live under `doc/arc42/adr/` (one AsciiDoc file per decision, per §7.1's note below), never as an Obsidian note — Obsidian only links to this ADR, it does not duplicate it:
   - Is the system staff-only (roles gate *endpoint/entity type*), or does Owner become a logged-in identity (responses must be row-level filtered to "their own" data)?
   - If staff-only: the exact role list and the read/write matrix per role × entity (Owner/Pet/Vet/Visit).
   - If owner-as-user: whether a Vet is further scoped to only their own assigned Visits, or any authenticated vet may act on any visit.
   - Which claim shape carries authorization (`roles: [...]` vs. OAuth-style `scope: "..."`), since that decides how `oauth2ResourceServer(...)` and every client's token handling get generated.
3. **A risk row**, `No authentication or authorization is currently enforced`, directly in `doc/arc42/11-risks-and-technical-debt.adoc`'s table (no separate file, no number — see §7.1's note on risks) — Score `3 (1 × 3)` (likelihood 1: today's exposure is dev/local only; impact 3: any request can read/write all data), Mitigation pointing at ADR 0004. Framed as an **accepted, tracked risk**, not an urgent defect.
4. **A one-line forward pointer** in `openspec/project.md` noting that a future change will introduce authorization and where its ADR lives, so an agent reading OpenSpec first (before Obsidian) still discovers the plan exists.

When the future plan is ready to execute, it: answers the ADR's open questions, flips its status to `accepted`, drafts the `## ADDED Requirements` delta as a working (non-persisted) OpenSpec change and applies it straight into `security/spec.md`, updates the risk entry's status, and only then implements `oauth2ResourceServer(...)` in `EsySecurityConfiguration` plus the corresponding UI changes in `client-shell` and both client repos. None of that implementation work happens in this plan.

## 7. Obsidian (`obsidian/`)

### 7.1 Structure

```
obsidian/
├── Domain/
├── Architecture/
│   └── patterns/       # detailed architecture patterns backing arc42 ch. 4/8
├── Backend/
├── Frontend/
├── Security/
├── Database/
├── Testing/
├── Building/

```

**Architecture decisions and risks are not Obsidian artifacts.** Each ADR is a single AsciiDoc file under `doc/arc42/adr/` (§6, chapter 9); every risk is a row — `Risk | Score | Mitigation`, no numbering — directly in `doc/arc42/11-risks-and-technical-debt.adoc`'s table (§6, chapter 11). Neither has a Markdown note here. A note in this graph that discusses a decision's rationale, an open question it raises, or a risk it relates to **links to** the ADR or risk table (e.g. in its `related:` frontmatter or body text) rather than duplicating any part of it. This keeps exactly one authoritative copy of each — under `doc/arc42/` — consistent with arc42 outranking Obsidian in the §1.1 precedence order.

Conventions (from the request, enforce via the `knowledge-maintainer` skill, §8):
- One fact per note, small and atomic.
- Standard Markdown links only (`[title](../Backend/note.md)`), no `[[wikilinks]]` — keeps the graph portable outside Obsidian.
- Never restate `openspec/`, `doc/arc42/` (including `doc/arc42/adr/`), `doc/concept/`, `doc/manual/`, `doc/service/` content — link to it.
- Every note carries frontmatter: `category`, `related` (list of relative links), `status` (`current` | `stale` | `superseded`), and `updated:` (date last checked/corrected against the code) — so `consistency-checker` can validate structure mechanically and enforce §1.1's rule that a note is a hypothesis about the code, not a fact in its own right.
- A note with `status: stale` or `status: superseded` carries a one-line explanation of why (see §1.1) and is never read as current guidance by any agent or skill.

**Agent-only maintenance.** The Obsidian knowledge graph is maintained **exclusively by AI agents through the skills in §8** — never by direct human edits to `obsidian/`. Human contributors may review notes and propose changes (issue, PR comment, conversation), but every update, link, metadata change, and structural modification is performed by an agent running `knowledge-maintainer` (or, for structural validation, `consistency-checker`), so the §1.1 verify-against-code discipline is actually applied every time, not bypassed by a quick manual edit.

## 8. Skills (`.agents/skills/doc/`)

Seven skills, each created by **running the `skill-creator` skill** (`.agents/skills/skill-creator/SKILL.md`) rather than hand-authored from scratch — one invocation per row below, giving it the purpose in the "Purpose" column as the request. `skill-creator` derives the front matter, section structure, and validation checklist for each new `SKILL.md`, so all seven end up consistent with each other and with the rest of `.agents/skills/*/SKILL.md` (`name`, `description` in single quotes, lower-case-hyphen directory name) without that consistency having to be re-specified here per skill.

| Skill | Purpose |
|---|---|
| `change-impact-analyzer` | Given a diff, determine which of arc42/OpenSpec/Obsidian/ADRs/risks are affected; produce a focused update checklist so nothing drifts silently. Flags any Obsidian note whose claim about the changed code may now be stale, per §1.1, even if no doc file was touched by the diff. |
| `openspec-maintainer` | Maintains `openspec/` as normative spec: runs the propose → apply → merge lifecycle entirely as working state (`changes/` is gitignored, never committed), applies deltas straight into `specs/` (no archive, no persisted change history — git history of `specs/` is enough), keeps specs technology-independent, blocks significant behavior changes from landing without a spec update first. Per §1.1, `openspec` ranks below `doc/arc42`/`doc/concept` and above `obsidian` — this skill never overrides an arc42 or `doc/concept` statement, it reconciles toward them (or flags the contradiction for a human if the two genuinely disagree about current-state fact, as opposed to openspec deliberately specifying a not-yet-implemented target per §5.3). |
| `knowledge-maintainer` | The **sole agent-facing writer** of `obsidian/` (§7.1 "Agent-only maintenance"): small atomic notes, no duplication, correct category, links to arc42/OpenSpec/ADRs/risks/implementation. Before writing or touching any note, checks its claim against the current code per §1.1 — on a contradiction, follows the code, corrects the note, and sets `updated:`; if it can't verify, sets `status: stale` with a one-line reason instead of guessing. Never treats a `stale`/`superseded` note as current guidance for anything it produces. |
| `arc42-overview-maintainer` | Maintains `doc/arc42/`: keeps it concise/stable, applies the "would removing this detail change a stakeholder's understanding" test, moves overflow to Obsidian. |
| `arc42-adr-maintainer` | Creates/updates ADRs as **single AsciiDoc files under `doc/arc42/adr/`** (one per decision — not an Obsidian artifact), links them from arc42 ch. 9. Also ensures any Obsidian note discussing the same decision *links to* the ADR instead of duplicating it. |
| `arc42-risk-maintainer` | Adds/updates rows **directly in `doc/arc42/11-risks-and-technical-debt.adoc`'s table** (`Risk \| Score \| Mitigation`, no numbering, `Score` = likelihood × impact each 1–3) — not an Obsidian artifact, no separate file per risk. |
| `consistency-checker` | Structural + cross-artifact validation: broken links, orphan notes, missing frontmatter, naming conventions, requirements without verification (test/story), tests/decisions without a source requirement. Phase D's own acceptance check is therefore: for each of the seven, confirm `skill-creator` was actually invoked (not skipped in favor of hand-writing) and that its own validation checklist passed before moving on to the next.

## 11. Sub-plan: `petclinic-svelte-ui` (standalone repository)

Mirrors §10 with the Svelte 5 + Vite stack (matches current `client-svelte`: Svelte 5, Tailwind 4 + daisyUI 5, RxJs services, Vitest, Playwright). Same sync mechanism, same Storybook-for-Svelte requirement, same CI shape, same parity checklist and cutover gate. Svelte also consumes REST only today, so its synced OpenSpec subset matches Angular's.

### 11.1 Sync mechanism (shared by both client repos)

- A manifest in each client repo (e.g. `openspec.sync.json`) lists which capability folders from the server repo's `openspec/specs/` to pull, resolved against a pinned server repo ref (tag or commit).
- A sync script (Node or shell, run manually or via a GitHub Action on demand — not on every push, to avoid churn) copies those folders verbatim into the client repo's `openspec/` directory, stamping a `SYNCED_FROM` marker (source ref + timestamp) at the top of each copied file.
- Result is **self-contained and diffable** (a `git diff` in the client repo shows exactly what changed upstream) but is explicitly a **duplicated, potentially stale copy** — the manifest + marker make staleness detectable, not automatic; keeping it current is a manual/scheduled step, not silent magic.
- The client repo never edits synced files directly; changes flow server-repo-first (OpenSpec change drafted as working state, applied straight into `specs/`, committed → re-synced). Only `openspec/specs/` is ever synced — `openspec/changes/` never exists in the server repo's committed history, so there's nothing there to sync in the first place.

### 11.2 Decommission gate (applies to both `app/client-angular` and `app/client-svelte` in *this* repo)

Only after **both** conditions hold for a given client:
1. The standalone repo (§10 or §11) is fully built, its CI is green, and it has been verified at feature parity with the in-repo client.
2. A deliberate cutover decision is made (deployment config in `app/deploy` repointed, or the standalone repo takes over deployment entirely).

Then, as a separate follow-up change (not part of this plan):
- Remove `app/client-angular` or `app/client-svelte` from this repo.
- Remove the corresponding `include 'app:client-*'` from `settings.gradle`.
- Update `playwright.test.sh`/`playwright.setup.sh`, `app/deploy/compose.yml`, `pages/html/client-*`, `AGENTS.md`'s artifact-location tables, and `doc/concept/angular`/`doc/concept/svelte`.
