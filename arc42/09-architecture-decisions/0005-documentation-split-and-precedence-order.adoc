== Context and problem statement

This repository maintains several documentation artifacts that can describe overlapping aspects of the same system: bird's-eye architecture facts (`arc42`), per-technology-stack implementation guides (`doc/concept`), a normative, implementable behavior contract (`openspec`), and an explanatory knowledge graph (`obsidian`), alongside reference documentation (`doc/service`, `doc/manual`).
Without a clear division of authority and a defined precedence, these artifacts can silently drift out of sync as the system evolves, and it becomes unclear which one a reader — human or agent — should trust when two disagree.
See xref:{relrootdir}/arc42/04-solution-strategy/documentation-split-and-precedence.adoc[arc42 ch. 4: Solution Strategy], xref:{relrootdir}/arc42/10-quality-requirements/overview.adoc[ch. 10: Quality Requirements], and link:../../AGENTS.md[AGENTS.md].

== Considered options

=== Split documentation by authority with an explicit precedence order

Each location owns exactly one kind of fact: `arc42` for bird's-eye architecture; `doc/concept` for per-stack implementation guides; `openspec` for the normative backend behavior contract; `obsidian` for the explanatory knowledge graph maintained only by AI agents.
When two locations disagree about a current-state fact, precedence is: code and tests, then `arc42`, then `doc/concept`, then `openspec`, then `obsidian`.
An `obsidian` note is a hypothesis about the code, never an independent fact.

=== A single combined documentation source

Rejected because bird's-eye architecture facts, an implementable behavior contract, and deep rationale notes serve different audiences and change at different rates.
Combining them either bloats the bird's-eye view or buries architecture facts in exhaustive technical notes.

=== No defined precedence, resolve conflicts ad hoc

Rejected because it leads to silent, undetected disagreement between artifacts as the system evolves.

== Decision

Keep the documentation split and resolve disagreements in the precedence order above.

=== Consequences

* The `consistency-checker` skill can mechanically validate structural rules and flag cross-artifact contradictions in precedence order.
* Every significant behavior has one normative source under `openspec/specs/*` (see ch. 10's Traceability quality goal).
* Adding a new kind of fact requires deciding which single location owns it.
