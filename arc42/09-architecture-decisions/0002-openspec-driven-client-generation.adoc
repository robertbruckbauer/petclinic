== Context and problem statement

Two independent browser client stacks needed to stay behaviorally identical while being free to fully regenerate their implementation when their framework or style guidelines change significantly.
Keeping generated client code in the same repository/history as the specs that drive it made "rebuild from scratch" ambiguous.
See xref:{relrootdir}/arc42/04-solution-strategy/openspec-behavior-contract.adoc[arc42 ch. 4: Solution Strategy].

== Considered options

=== OpenSpec contract with clients in separate standalone repositories

`openspec/specs/*` in this repository was the single normative contract every client was generated from.
Each client lived in its own standalone repository and pulled a copied, diffable subset of the relevant OpenSpec capabilities via an explicit sync step — not a live reference into this repository.

=== Monorepo with client packages

Rejected because it couples client release/build tooling to the server's Gradle build and makes "rebuild from scratch" mean "edit in place" rather than "regenerate."

=== Git submodule pointing at openspec/

Rejected because submodules are operationally painful and still couple the client repo's history to the server repo's; a copied, stamped snapshot is simpler to reason about even though it can go stale.

== Decision

This ADR is superseded.
OpenSpec in this repository covers backend capabilities only; client generation in separate repositories is no longer the adopted direction.

=== Consequences

* Historical client repositories were self-contained: clone one, and the spec subset needed to regenerate it was right there.
* Keeping a client repo's spec copy current was a manual/scheduled step, not automatic.
* No later ADR replaces this decision; backend OpenSpec remains the normative contract for this repository.
